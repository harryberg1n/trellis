# trellis

trellis records what an AI coding agent does in a repository and puts walls and policies in front of the tool calls that have caused incidents. This is milestone M0: the recorder and the walls.

Install: download the binary for your platform from the latest GitHub release, check it against `sha256sums.txt`, and put it on your `PATH`. Then run `trellis version`.

## Verbs

`trellis help` prints the same list.

- `trellis version` (also `--version`) prints the version and commit.
- `trellis hook <event>` records one agent hook payload read from stdin. The hooks that `install` adds run it; it is not typed by hand.
- `trellis report [--issue]` prints speed, cost and labels. `--issue` files the aggregate on `harryberg1n/trellis`, which needs an authenticated `gh`. What the report could not read is a `not read: …` line in the body, so a filed issue says it. A mean over fewer than 10 samples prints `n=<k>, no interval`. Transcripts include the session's `subagents/*.jsonl`, counted once per request; lines or files that could not be read are counted (`transcript lines skipped`, `transcript files not read`). In the filed issue a model id with no price is shown as its size (`large model`, `medium model`, `small model`, `other model`). Under the tree count it says what made the trees defect (within 14 days of the merge: reverted, a fix touched its lines, a later commit or PR named its PR, an escape issue named its PR, each with its count) and what pending and clean mean. A session's usage is the lines of its transcript that carry its `sessionId`; a session continued after a context compaction, whose own transcript file does not exist, is read from the transcript beside it that holds its lines. Prices are the list prices of the Claude API reference (cached 2026-10-06), `claude-opus-5-5`, `claude-sonnet-5-5`, `claude-fable-5-1` and `claude-haiku-5-5` (with its price above a 100K-token prompt) included.
- `trellis allow <row-id>` waives the next deny of a wall once, for ten minutes, in this repository: the token is repo-wide, shared by the primary and every tree, and whichever is denied first consumes it. Rows with no override are refused.
- `trellis install [--config-dir D] [--repo R] [--dry] [--allow-dev]` pins this binary under the state root, wires the six hook entries once per user in `settings.json` of the Claude config directory (`--config-dir`, else `$CLAUDE_CONFIG_DIR`, else `~/.claude`; an existing file is copied beside itself as `settings.json.pre-trellis-<unix seconds>` before its first change), writes `trellis.toml` at the root of the checkout you run it in when that has none (run in a tree, the file is the tree's: commit it there and merge it, and the repository is on from the merge; the wiring and the record stay on the primary), and removes trellis's entries from the repository's `.claude/settings.local.json` and from each linked worktree's. It prints one line per action; `--dry` prints them with `would` and does nothing; `--allow-dev` pins a build whose version is `dev`, which is refused otherwise.
- `trellis doctor [--config-dir D] [--repo R]` checks the user-level hooks against this binary and the state root, names each event that is missing, says `trellis.toml missing: this repository is off` when the repository has none, and names a project-local file that still holds trellis entries (every event would fire twice). A clean box prints `doctor: ok`.
- `trellis eject [--config-dir D] [--repo R]` removes exactly what `install` added, from the user-level file and from the repository's project-local files. It leaves `trellis.toml`, which is the repository's own committed file.
- `trellis update [--config-dir D] [--to VERSION] [--dry] [--allow-dev] [--forget-missing]` fetches the newest release (or `--to`), verifies its sha256, pins it, points the user-level hooks at it (only a file that already holds trellis hooks; `update` never installs), removes trellis's entries from the project-local files of every recorded repository and its trees, replaces the binary on `PATH` and sweeps old pins; it says when the `trellis` found on `PATH` is another file than the one it replaced, and removes staging directories left by an earlier update that are older than a day (also when it finds nothing to update). When already at the version it still rewires hooks that point at another one. A recorded path that is not a repository root is kept in the record and reported; `--forget-missing` drops it. `update` needs an authenticated `gh`.
- `trellis tree new <name> [--path P]` opens a tree: a git worktree on a new branch of that name, cut from `origin`'s default branch, in a sibling directory. A name cannot be only digits, begin with a dash or be one `git check-ref-format --branch` refuses, and a name that is already a branch on `origin` is refused with the `git worktree add --track` line that tracks it.
- `trellis tree sync` fetches `origin` and rebases this tree onto its default branch. It refuses a tree with uncommitted tracked changes before fetching (exit 2: `uncommitted changes: commit or stash, then sync again`).
- `trellis tree merge [<name>] [--check CMD] [--rebase]` runs the optional check (its output is shown as it is written; a failure names its last line), pushes with `--force-with-lease --force-if-includes` (a push refused because `origin` holds commits the tree lacks exits 2 with how many and `git pull --rebase origin <name>` as the next step), opens or finds the pull request (titled from the branch's first commit), waits for its checks, squash-merges it bound to the head the checks judged (`--rebase` keeps the commits; a head that moved since exits 2: `the PR head moved after it was judged`), deletes the branch on `origin` (silently when GitHub already deleted it with the merge) and removes the tree. With `<name>` it merges that tree from anywhere, the primary checkout included, so the caller's shell is not left in the directory the merge removes; from the primary without a name it says to name one. When the tree's `.github/workflows` hold workflow files and none of them can run on this pull request (only `push` to other branches, tags, `schedule`, `workflow_dispatch`, `merge_group`, `release` and the like), it says `no workflow runs on a pull request into <default>` and does not wait for checks; a workflow file it cannot read (a flow mapping, an anchor, a filter beyond `*` and `**`, an unknown event) counts as one that can run. A pull request with no checks is merged only when no workflow run of its head is still queued or in progress; that wait ends after 30 minutes (exit 2), and a run list that cannot be read is an error, never "no run". A check that exceeds its 30 minutes says `timed out after 1800s`. `tree new` fetches with `--prune`, so a branch deleted on `origin` does not refuse its name. A `gh` read that fails for a network or rate-limit reason (HTTP 429, 500, 502, 503, 504, a cut-off answer, a timeout, an offline `error connecting to`) is retried up to 5 times, 5 seconds doubling, or the `Retry-After` it names (at most 2 minutes); the waiting lines start with the UTC time. The push, the merge and the delete of the merged branch are retried the same way on a server error (`remote: Internal Server Error`, `The requested URL returned error: 502`, GraphQL's `Something went wrong while executing your query`); a merge that answered an error is first read back, so a 502 from a merge GitHub made counts as the merge, and `Merge already in progress` is waited out. After the push, the merge waits up to 2 minutes for the pull request to show the pushed head before it says `head moved`. A green `--check` is kept per head in the tree's git directory: a merge run again on the same head with the same command says `check passed on <sha> already: not run again`. A branch delete that still fails is a warning with the command that deletes it; the exit code says whether the PR merged. Each red check shows the failing lines of its own job. It needs an authenticated `gh` (`gh is not installed` and `gh is not logged in` are told apart). Every git child has a deadline: 120 seconds for a fetch or a push, 10 minutes for any other, and a timeout says `git push: timed out after 120s`. A repository with no remote lands the tree locally as one squash commit (`--rebase`: a `--no-ff` merge) and needs no `gh`; an untracked file in the primary at a path the tree changes is refused first (exit 2, each path named, nothing changed): remove it there or commit it, then merge again. A repository with a remote needs `origin` and `origin/HEAD` (`git remote set-head origin -a`); trellis does not guess a base.
- `trellis tree rm [<name>] [--force]` removes a tree and its branch. It refuses uncommitted work, and commits that are neither merged into the default branch (a squash- or rebase-merged pull request counts, found with `gh`; in a repository with no remote, a `Merge tree <name>` commit on the default branch) nor pushed to the branch's upstream, unless `--force`. Its refusal names `tree drop`, which keeps the work instead.
- `trellis tree adopt <branch> [--path P]` makes a tree of a branch that already exists, in the usual sibling directory: a branch on `origin` (the tree tracks it), or a local branch with no tree. `tree new` refuses a name that is already a branch on `origin` and names `tree adopt` instead.
- `trellis tree drop [<name>] --reason R` removes a tree and its branch and keeps everything it held: the branch tip, and its uncommitted work (untracked files included, ignored ones not) as one commit on top, built from objects only, at `refs/trellis/dropped/<name>-<UTC time>`. It prints the `git worktree add` line that restores the tree and records `tree.dropped` with the reason (the tree is then abandoned). Nothing is lost, so it needs no `--force` and no override: it is how an agent drops a lane that is worthless but not merged, where `git branch -D` and `git worktree remove --force` meet `discard-uncommitted`. origin is left alone.
- `trellis tree list [--size]` lists every worktree of the repository, trellis-made or not: branch, commits ahead of the default branch, uncommitted files, pull request state (`merged`, `open`, `closed`, `none`, `?` when gh cannot say), age of the last commit, and what `tree prune` would do (`remove`, `prune(missing)`, or `keep(<why>)`: `uncommitted`, `open-pr`, `unmerged`, `no-merge`, `detached`, `you-are-here`). Directories beside the primary named like trees that git does not list are shown as `orphan`. `--size` adds the size on disk (#50).
- `trellis tree prune [--dry] [--backup]` removes every tree whose pull request merged with its tip (squash merges included, read with `gh`; with no remote, a `Merge tree <name>` commit that records the tip) and that holds no uncommitted work, and forgets with `git worktree prune` the trees whose directory is gone. `--backup` also removes every other tree after keeping all it held as `tree drop` does, recorded as `tree.dropped` with the reason `tree prune --backup`, and pushing it to `origin` as `backup/<name>`. The tree the caller stands in is always kept, a gh that cannot answer keeps the tree, and orphan directories are named, never deleted. `--dry` prints the plan.

A repository is on once `trellis.toml` is committed at its root, found by walking up from the working directory to the first `.git`; a linked worktree is on once the file is in it, by merging it or by running `trellis install` there. Anywhere else, and under `TRELLIS_OFF=1`, the hook exits 0 with no output and writes nothing. Everything a tree writes goes to the store of the primary checkout.

## Settings

`trellis.toml` turns a repository on, and may set what the tree verbs do. Every key is optional; an unknown table or key, or a value of the wrong kind, stops the verb with the file's line (`trellis.toml:2: unknown key tree.new.lnk`).

```toml
[tree]
remote = "github"            # the remote trees push to and are cut from; default origin

[tree.new]
link = ["node_modules"]      # paths of the primary checkout linked into a new tree, first
run = ["make warm"]          # then run in the new tree, shown as they run

[tree.merge]
checks = "none"              # never wait for CI: the gate is the local --check; default "auto"
# require = ["test-linux"]   # or: check names that must appear before the merge (at most 30 minutes)
```

`tree new` reads the new tree's own `trellis.toml` (what it was cut from). A link whose target is missing in the primary is a warning, and a link git would list as untracked is added to the repository's exclude file, so the tree stays clean; on Windows a directory gets a junction when a symbolic link is not allowed. A command that fails stops `tree new` with its last line and the tree's path (the tree stays). `tree merge` reads the tree's `trellis.toml`: `checks = "none"` says `trellis.toml says checks = "none": not waiting for checks`, and `require` waits until every named check is on the pull request, naming the ones still missing, and exits 2 after 30 minutes with `required checks did not appear in 1800s: <names>`. `checks = "none"` and `require` exclude each other.

## Walls

A deny is `trellis: <row>: <cause>. Override: <command>.`, one line except the secrets deny, which lists its findings under it; the command is `trellis allow <row>` or `none`. What the walls read, where it is not obvious:

- Command names are matched without case on Windows (`Git reset --hard`, `GIT.EXE commit --no-verify` are `git`); elsewhere `Git` is not `git`.
- `main-commit` lets the primary checkout move to its own upstream: `git merge origin/main`, `merge --ff-only @{u}` or a bare `git merge` on the default branch pass when `branch.<name>.remote` and `.merge` name it, since those commits were judged on the way into origin. A merge of anything else, a second ref, or `--no-ff` is still a main commit (found as the first deny on honest work of the live run, 2026-10-18).
- `main-commit` judges a push from the primary by the refs it writes on the remote: `git push origin <sha>:refs/heads/backup/x`, `push origin --delete <branch>`, `push origin :<branch>`, `push origin <branch>` and tags pass when none of them is the default branch. A push with no refspec, `HEAD`, `--all`, `--branches`, `--mirror`, `--prune`, a wildcard, or a bare `<src>` to a remote with `remote.<name>.push` set is still a main commit (#50, #52: a backup push and a branch delete were denied, and `gh api -X DELETE` went around the wall).
- `discard-uncommitted` measures `git clean` with `-x` or `-X` over the ignored files too: `clean -fdx discards 1 untracked file, 1 ignored file` (`-X` counts only the ignored ones). `git stash drop` and `git stash clear` on a repository with no stash entry pass; with one they say `stash drop discards a stash entry for good`.
- Each deny names the step that keeps the work. `discard-uncommitted` adds `git stash push -- <paths>` for `checkout -- <paths>` and `restore <paths>`, `git stash push` for `reset --hard`, `git stash push --include-untracked` (or `--all` with ignored files) for `clean`, `git branch -m <b> dropped/<b>` for `branch -D`, and `trellis tree drop <branch> --reason <why>` for `worktree remove --force`. `primary-write` adds `trellis tree new <name>` and the path it makes. In the reports of #50 and #52 every one of these denies was unresolved, and `git show HEAD:<path> > <path>` discarded the same work with no wall in the way.
- `undercover` reads the text of `git commit` and `git merge` (`-m`, `-F`), the title, squash subject and body of `gh pr create|edit|merge` (`-t`, `--title`, `--subject`, `-b`, `--body-file`), and the identity a commit is made with: `--author=` or `--author <ident>`, and `-c user.name=` or `-c user.email=` before the verb, for the verbs that write a commit (`commit`, `merge`, `cherry-pick`, `revert`, `am`, `rebase`, `pull`; `git log --author=` is a search and passes). A vendor address (`@anthropic.com`, `noreply@openai.com`, `cursoragent@cursor.com`, `<digits>+copilot@users.noreply.github.com`) is a deny on any line or in an identity: `the author or committer identity of this commit carries a vendor address ("noreply@anthropic.com")`. A name alone is not a tell.
- `secrets` runs gitleaks over the staged changes (`gitleaks git --staged` from 8.19, `protect --staged` before; the version is asked once per binary path and mtime and kept in `tool-versions.json` in the state root) and, for a commit that stages as it goes, over the uncommitted changes. A finding is listed as `file:line  rule  fingerprint <fingerprint>`, followed by the three ways to clear a false positive: `gitleaks:allow` in a comment on that line, the fingerprint in `.gitleaksignore`, or an `[allowlist]` in `.gitleaks.toml`. The row has no override.
- A rebase in progress keeps its branch: the recorder reads `rebase-merge/head-name` and `rebase-apply/head-name` from the worktree's own git directory, so edits during a conflict stay on the tree, not on `detached-<sha>`. A rebase of the default branch in the primary checkout therefore counts as being on it, so `primary-write` denies the edits of its conflict resolution: the primary is merge-only, and `trellis tree merge` refuses a primary stuck mid-rebase.

## Exit codes

0 done. 1 an error. 2 a failure you can fix and run again (red or cancelled checks, a conflict, a branch that is behind or blocked, a head that moved), or a usage mistake. 130 `tree`, `update` or `report` was interrupted by Ctrl-C or a terminate signal; the running child and its process tree are ended first, and a local squash in flight is undone. On Linux a child also dies with trellis when trellis is killed outright (SIGKILL, a crash).

## Tests

`go test -race -shuffle=on ./...` is the CI run. Hook latency is not a test: every event the hook writes carries `took_ms`, and `trellis report` prints p50 and p95 per hook against the criteria over the live log. A nightly flake hunt runs `go test -race -shuffle=on -count=5 -json` on Linux and Windows and keeps the JSON stream and a plain log as an artifact; a non-zero exit with an empty stream is named an infrastructure failure.

## Versions and releases

The `VERSION` file at the repository root is the source of truth for the version (`.claude-plugin/plugin.json` must equal it, a test enforces that). A push to `main` that changes `VERSION` is a release: the workflow builds `linux/amd64`, `linux/arm64` and `windows/amd64`, smoke-runs the Linux binary and requires its `version` to name the tag, then creates the GitHub Release `v<VERSION>` bare and uploads the binaries with `--clobber`, `sha256sums.txt` last. A re-run after a partial upload finishes it; a release that has its `sha256sums.txt` is left alone, and a `gh release view` failure other than "not found" stops the run. So a VERSION bump is a release. A hand-pushed `v*` tag also builds, and must equal `v` plus the content of `VERSION`; the workflow fails otherwise.
